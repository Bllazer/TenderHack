# Ручная проверка TenderHack

Использовать только приложенные данные: карточки `TenderHack_real_cases.csv`, сценарии `TenderHack_tests.csv` и их XML-ссылки. REAL — исходные карточки Excel; SRC — проверки правил XML. Изменение единиц или удаление сведений ниже — явно указанный вариант существующей карточки, а не внешний пример.

Перед проверкой: API `/api/health/ready` отвечает 200, фронтенд подключён к этому API. Сохранить дату, версию каталога, версию приложения. Для каждого сценария записать PASS/FAIL/BLOCKED, фактический результат и скриншот. Отсутствие функции — FAIL по требованию, недоступный API — BLOCKED. Автоматический PASS не заменяет проверку поведения интерфейса.

## Приёмочные сценарии задания и жюри

| № | Действия | Ожидаемый результат |
|---|---|---|
| M01 | Ввести `description` REAL-001 целиком. Проверить предложенные типы. Подтвердить «Дрель ручная электрическая». | Правильный тип доступен; система показывает извлечённые характеристики и дальнейшее действие. Ранжирование не выдаётся за доказанный конечный код. |
| M02 | Из той же карточки оставить только слово «Дрель». | Система предлагает уточнить назначение/тип; бытовая, механическая и медицинская дрель не подменяют друг друга без подтверждения. |
| M03 | На шаге выбора типа отказаться от предположения и вручную указать точное название категории из XML. | Можно исправить тип, введённый текст сохраняется. Характеристики и кандидаты пересчитываются для нового типа. Если ручного ввода нет — FAIL функциональности интерфейса. |
| M04 | Начать с типа электрической дрели. Последовательно добавить свойства из `confirmed_request_json` REAL-002. | Показывается актуальное число кандидатов и причина исключения. Дополнительное непротиворечивое свойство не возвращает исключённые коды. Если признак общий, число может остаться прежним. |
| M05 | В REAL-001 изменить только мощность `650 Вт` на `0,65 кВт`. | Одна и та же физическая величина даёт одинаковое множество кодов и одинаковые результаты проверки мощности. Нормализация объяснена. |
| M06 | Открыть REAL-021: в названии рост `110 сантиметров`, в свойствах `110.00000 см`. | Нет ложного конфликта; отображается единое нормализованное значение. Текущий автоматический тест выявляет нарушение. |
| M07 | Открыть REAL-022 с «Наличие карманов Да» и «Наличие нарукавников Нет». | Оба сведения относятся к своим свойствам. Нарукавники не превращаются в отрицание карманов. Неизвестное справочнику свойство сохраняется отдельно. |
| M08 | В REAL-001 проверить высоту, глубину и ширину **упаковки**. | Размеры упаковки не используются как размеры самого товара. Пользователь видит сохранённые сведения либо объяснение их неприменимости. |
| M09 | Взять SRC-сценарий с `outcome=incompatible`. Передать его описание и attributes через интерфейс, если есть отдельные поля. | Ошибка привязана к конкретному свойству; показаны значение, ограничение источника и способ исправления. Код с нарушенным ограничением не выбирается. |
| M10 | Взять соседние SRC-сценарии одной характеристики: ниже границы, на границе, выше. | Результаты соответствуют `expected_json`. Строгая и включительная границы не смешиваются. Указано, почему значение допустимо/недопустимо. |
| M11 | Для REAL-021 выбрать только «Половой признак: Для девочки». Подтвердить код из `incomplete_request_json`. | Единственный код и незаполненные обязательные поля представлены отдельно: код доступен, рост и ткань требуют дополнения. Нельзя выдавать карточку за полностью заполненную. Текущая политика API нарушает этот принятый критерий жюри. |
| M12 | Оставить в той же карточке только «Халат детский», убрать половой признак. | Не выбирается произвольный код для мальчика/девочки. Предлагается конкретный различающий вопрос. |
| M13 | Если КТРУ-позиции имеют одинаковые ограничения, открыть соответствующий сценарий `acceptance_review` основного CSV. | Система объясняет, что по имеющимся признакам коды не различить. Повторение одинаковых вопросов не приводит к выдуманному выбору. |
| M14 | В REAL-021 проверить несколько исходных цветов и видов застёжки. | Допустимые множественные значения сохраняются; система не оставляет молча только первое. Где свойство однозначное и значения конфликтуют, требуется уточнение с объяснением. |
| M15 | Добавить характеристику из той же карточки, отсутствующую в выбранном КТРУ, например исходное название элемента одежды. | Сведения сохраняются, не сопоставляются с похожим по написанию чужим свойством. Показано происхождение: КТРУ, словарь портала или дополнительное свойство. |
| M16 | Сохранить новое название свойства из M15. Начать новый товар и повторно вводить то же название. | Предлагается ранее сохранённое унифицированное название; не появляются дубли. Если реестра нет, зафиксировать FAIL требования повторного использования, а не PASS stateless API. |
| M17 | Открыть исходную карточку с большим числом характеристик, например REAL-022. | Явные корректные сведения не требуют подтверждения по одному. Вопросы задаются только для ошибок, неоднозначности и данных, необходимых для выбора. |
| M18 | Проверить итоговый код по `source_xml_json`: версия, название, статус и свойства. | Используется соответствующая последняя ACTIVE-версия из поставки. Старые версии не предлагаются как самостоятельные актуальные варианты того же кода. |

## Управление состоянием и интерфейс

| № | Действия | Ожидаемый результат |
|---|---|---|
| M19 | Начать печатать название REAL-001; сделать паузу; продолжить. | До нажатия кнопки текст не отправляется и шаг не переключается. Ввод и фокус не теряются. |
| M20 | После результата изменить мощность; затем удалить её. | Результат пересчитывается по текущим данным. Старый код/подтверждение не остаётся действительным. Удаление ограничивающего свойства может увеличить множество кандидатов. |
| M21 | Перейти назад из уточнения, исправить тип, снова продолжить. | Сохраняются исходные сведения; старые ответы и подтверждения не применяются к новому типу автоматически. |
| M22 | Через существующий сценарий исправления основного CSV проверить принятие и отклонение предлагаемой поправки. | Обе кнопки работают. Смысловое исправление требует согласия; отклонённое исходное значение не исчезает. Понятно, что и почему изменено. |
| M23 | На числовой вопрос выбрать «Не знаю»; затем отдельно указать `0`, если он допустим по выбранному SRC. | Неизвестное, пустое и нулевое значения различаются. Неизвестное не подтверждает характеристику и не превращается в ноль. |
| M24 | Отправить описание; сразу изменить его и повторить отправку. | Поздний ответ старого запроса не заменяет результат нового. Повторный клик не создаёт несколько конкурирующих переходов. |
| M25 | Остановить API во время запроса, затем запустить его и повторить. | Понятное сообщение о недоступности сервиса, возможность повторить, введённые сведения сохранены. Ошибка ресурсов не называется ошибкой пользователя. |
| M26 | Пройти сценарий клавиатурой, затем при узком окне и масштабе 200%. | Видны текущий шаг, основной вопрос, кнопки и ошибки. Нет обрезанных полей, перекрытия фиксированной панелью и скачков прокрутки. Фокус понятен. |
| M27 | Дойти до результата, начать новый товар, вернуться к первой карточке. | Состояния товаров не смешиваются. Если история не поддерживается, её отсутствие не выдаётся за сохранение; предупреждение о потере текущего ввода понятно. |

## Как оформлять дефект

Указать M-номер, REAL/SRC-номер, исходный запрос, ожидаемый результат из CSV/XML, фактическое поведение, каталог/API-версию и скриншот. Для неверного кода приложить карточку позиции XML, для неверной характеристики — исходный фрагмент Excel. Не исправлять эталон по ответу модели.

Этот чек-лист покрывает функции и интерфейс. Не является утверждением, что все функции уже реализованы. Реестр новых характеристик и выдача уникального кода при неполных обязательных свойствах требуют явной проверки реализации.
