# Эталонные сценарии из реальных карточек

Из корня TenderHack, при работающем локальном API:

```powershell
.\backend\.venv\Scripts\python.exe run_real_tests.py --base-url http://127.0.0.1:8001
```

Файлы: `TenderHack_real_cases.csv`, `run_real_tests.py`, `real_cases_manifest.json`, `real_test_report.json`. Прежний набор из 140 сценариев не заменён.

## Происхождение ожиданий

Выбраны 30 реальных карточек из поставки Яндекс Диска: по пять ударных дрелей, письменных столов, ученических стульев, трикотажных футболок, производственных и детских халатов. Отбор по явному названию семейства; детские халаты для уроков труда исключены из однозначной разметки бытового семейства. Это целевая выборка для поиска ошибок, не случайная выборка для измерения точности всего каталога.

Каждая строка содержит Excel, номер исходной строки, ID СТЕ, неизменённые характеристики и ссылки на XML с кодами/версиями. Использована последняя найденная ACTIVE-версия конечной позиции. Хеши исходных файлов сохранены в манифесте. Название семейства сопоставлено явно; прогнозы модели не использованы для разметки.

Ожидания значений рассчитаны отдельно от production-кода: точное сопоставление перечислений без учёта регистра, числовые альтернативы и объединение интервалов через Decimal, включительность границ из XML, коэффициенты перевода единиц. 78 сопоставлений относятся к 23 карточкам. Для семи карточек без надёжного прямого сопоставления свойства выполняется проверка поиска; они не объявлены проверенными по значениям.

## Что именно проверяется

- `retrieval`: нужное семейство попало в первые пять предложений по оригинальному названию и характеристикам карточки.
- `source_constraints`: явно сопоставленные характеристики проверены по XML; оставшееся множество кодов совпадает с независимым пересечением ограничений. Здесь используется каноническое название семейства из XML, чтобы изолировать проверку характеристик от разбора названия конкретной модели.
- `natural_language`: тот же эталон проверяется при вводе оригинального текста без заранее подготовленных attributes. Поэтому этот этап обнаруживает ошибки извлечения и сопоставления.
- `clarification_funnel`: последовательное добавление известных характеристик не возвращает исключённые позиции, сохраняет семейство и проверяет ограничения каждого шага. Проверка не требует искусственного уменьшения числа кодов от неразличающей характеристики.
- `unique_code_confirmation`: когда независимое пересечение оставляет единственный код, его явное подтверждение даёт именно этот код. Это условный сценарий для размеченного подмножества характеристик, не безусловный конечный код для исходной карточки со всеми ещё не сопоставленными сведениями.
- `jury_unique_incomplete`: производный сценарий из REAL-021. Вводится только половой признак «Для девочки». XML оставляет один код, обязательные рост и тип ткани не заполнены. Согласно принятому требованию жюри, подтверждённый уникальный код должен показываться с предупреждением о незаполненных свойствах. Этот критерий отличается от текущей более строгой политики API.

NOT_LABELED означает отсутствие эталона значения для конкретного этапа, а не успешную проверку этого этапа. Каждый этап запускается отдельно: провал ранжирования не скрывает результат проверки ограничений.

## Результат запуска 11.10.2026

| Этап | PASS | FAIL | NOT_LABELED |
|---|---:|---:|---:|
| Поиск семейства | 30 | 0 | 0 |
| Явные характеристики и множества кодов | 23 | 0 | 7 |
| Разбор исходного текста | 16 | 7 | 0 |
| Последовательное уточнение | 11 | 0 | 0 |
| Подтверждение единственного кода | 6 | 0 | 0 |
| Единственный код с неполной карточкой | 0 | 1 | 0 |

Отчёт содержит исходные ID, этап, ожидаемое расхождение и полный ответ API для проваленных проверок. Exit code 1 ожидаем, пока присутствуют FAIL. Это не сбой запускателя.

Подтверждённые примеры для исправления backend:

1. REAL-021: «Рост 110 сантиметров» и «Рост 110.00000 см» объявлены конфликтом, хотя это одинаковая величина.
2. REAL-022 и следующие производственные халаты: сведения о других элементах одежды превращаются в факты о карманах. Например, исходное «Наличие нарукавников Нет» попадает в «Наличие карманов Нет» наряду с исходным «Наличие карманов Да».
3. REAL-021, отдельный критерий жюри: единственный код после выбора полового признака не выдаётся из-за неполноты обязательных свойств.

FAIL на исходном тексте не означает, что виновата только E5: тест включает извлечение фактов, нормализацию, сопоставление свойств и итоговую проверку. Необходим разбор конкретного ответа API. Противоречивые исходные данные также требуют корректного уточнения вместо выдуманного исправления.
