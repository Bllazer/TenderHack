## 6. Форматы данных: что важно знать

### Два формата факта, не путать

**Формат API и фронтенда** (`app/schemas.py:Fact`) — значения строками:

```json
{"id": "text:0:20:0", "name": "Тип питания", "value": "От сети", "unit": null,
 "raw": "...", "span": [0,20], "source": "text", "subject": "product",
 "negated": false, "unknown": false, "mappings": []}
```

**Формат контракта C и D** (`algorithms/contract.py:Fact`) — значения типизированы:

```json
{"fact_id": "...", "def_id": "...", "name": "...", "kind": "number", "value": 650.0,
 "unit": {"code": "212", "text": "Вт"}, "operator": null, "polarity": "affirmed",
 "negation": null, "span": [12,22], "extraction_method": "...",
 "extraction_confidence": 0.9, "definition_alternatives": []}
```

Обязательные по README: `kind`, `value`, `def_id`, `unit`, `extraction_confidence`,
`polarity`. **`fact_id` необязателен, но заполнять его обязательно** — см. §8.

`unit.text` — написание из текста, `unit.code` — код ОКЕИ. Переводить не нужно,
приведение к единице характеристики делает C.

### Выход модели — документ

`{"source", "schema_version", "items": [{"position_code", "title", "pool", "facts"}]}`
Ключи документа и item совпадают с `algorithms/samples/stage_model_output.json`;
факт богаче на `fact_id`, `operator`, `polarity`, `negation`, `span`,
`definition_alternatives` — все они есть в `contract.py`.

### Порог уверенности

`HARD_FACT_MIN_CONFIDENCE = 0.6`. Факт ниже порога проверяется, но **не должен
исключать код**. `is_hard = polarity == "affirmed" and confidence >= 0.6 and not problems()`.

## 7. Исследование модели A: что выяснено

### Как устроен матчер харнесса

`algorithms/validation_run.py:PropertyMatcher`:

* словарь строится по **всему** корпусу: 54 190 конечных позиций, 234 363
  характеристики, шаблоны пропускаются;
* `by_normalized` — 14 928 ключей; **12 058 из них (80,8 %) дают ровно один код**,
  2 870 (19,2 %) — больше одного. Проверено заново в сессии закрытия по
  `catalog.json`: ключей 14 947, уникальных 12 070 (80,8 %) — расхождение с 14 928
  в пределах нормализации, вывод не меняется. По корпусу различных имён 14 974;
* `resolve` отдаёт `def_id`, только если имя глобально уникально, иначе
  `ambiguous_name` с уверенностью **ровно 0.6** — на самом пороге;
* `split_fragment` принимает только имена из словаря, иначе фрагмент «не разобран»;
* `chars_by_name` в `ktru_index.py`: сначала точное совпадение, затем **подстрока**
  (`«Высота упаковки»` находит `«Высота»`).

### Замеры по данным

* 360 карточек СТЕ, 4 631 употребление фрагментов, 638 различных имён.
* **80,1 % имён фрагментов не совпадают ни с одним именем характеристики КТРУ**
  даже после нормализации регистра, отбрасывания хвоста после запятой и лемматизации.
  Точное совпадение — 18,0 %, без хвоста — 1,8 %, по леммам — 0,2 %.
* Часть «не найденных» — законно: «Бренд Walker», «Лицензиат Marvel» не
  характеристики КТРУ вовсе.
* **Имена характеристик уникальны внутри позиции: 100 %, ноль повторов на 52 255
  позициях.** Коды характеристик при этом **переиспользуются между позициями** семьи.
  Перепроверено по `catalog.json`: свойств 234 363 у 52 255 позиций из 60 087,
  повторов имён внутри позиции ровно 0.

### Что реализовано в `app/model_a.py`

Разбор и разрешение разделены намеренно:

* **разбор** идёт по словарю **всего корпуса** (14 709 ключей). Если строить его по
  пулу, теряется 965 фрагментов на 360 карточках — замерено: «Материал Полиэстер»,
  «Цвет синий», «Тип застежки Молния»;
* **разрешение** идёт по пулу позиций;
* сопоставление по леммам через `pymorphy3` (`«мощности»` → `«Мощность»`; точное
  совпадение это теряет);
* ступени уверенности: `exact` 0.95, `lemma` 0.90, `alias_lemma` 0.75,
  `partial` (вхождение) **0.55 — ниже порога**, чтобы догадка не выбрасывала код;
* ограничение по размерности единицы: «Масса» не сопоставляется с фактом в «мм»;
* каноническое имя характеристики подставляется в факт только для уверенных
  совпадений — иначе «Цвет» превращался в «Цвет мела»;
* карта единиц: **161 написание → 126 кодов ОКЕИ** (`model_a.UNIT_CODES`, см. §3) —
  против 24 кодов в `OKEI_SUPPORTED`, из-за узости которого 84 числовых факта шли
  без кода ОКЕИ.

### 8.1. Дыра с `fact_id` в `AlgorithmC` — доказана

```python
soft_ids = {f.fact_id for f, _ in soft if f.fact_id}   # None сюда не попадает
...
if fact.fact_id in soft_ids: ...    # мягкий факт -> unresolved
else: exclusions.append(...)        # ← ЖЁСТКОЕ ИСКЛЮЧЕНИЕ
```

Факт с уверенностью ниже 0.6 **без** `fact_id` жёстко исключает код, хотя README
обещает обратное. Проверено экспериментом:

```
уверенность 0.5, без fact_id  ->  incompatible   ← неверно
уверенность 0.5, с fact_id    ->  unknown        ← верно
```

Правка: отмечать мягкие факты тождеством объекта (`id(f)`), а не по необязательному
полю. После правки оба случая дают `unknown`.

**Почему это важно:** в их собственном `stage_model_output.json` `fact_id` нет
ни у одного из 34 фактов — то есть любой внешний выход модели попадал в дыру.
Мой `app/structured.py` заполняет `fact_id` всегда.

### 8.3. Счётчик `ложных исключений` ничего не показывает

```python
if result.flags.blocking and not result.survivors:
    soft = [f for f in facts if not f.is_hard]
    if soft: ...   # и только если снятие мягких фактов вернуло выживших
```

В 28 обнулённых карточках **мягких фактов не было ни одного** (проверено), только у
4 был `blocking`-флаг. То есть «ложных исключений: 0» означает «ни один случай не
подошёл под узкое определение», а не «потерь нет».

**Подтверждено на реальном пуле** (сессия закрытия): счётчик равен 0 у **обоих**
матчеров при 135 и 76 обнулённых карточках. Более того, среди 703 и 336 исключений
не было ни одного мягкого факта: оба матчера держат уверенность не ниже порога,
поэтому условие «есть мягкие факты» не выполняется почти никогда.

### 8.4. Причина обнулений — посторонние позиции в пуле

В пул рюкзака заглушка `pool_by_title` кладёт `«Цвет мела»`, `«Цвет чернил»`,
`«Тип подушки штемпельной»`. Факт «Цвет синий» сопоставляется с «Цвет мела» и
исключает позицию; когда весь пул такой, он обнуляется. Замена пула на реальный
поиск **починила 18 таких карточек** (рюкзаки Centrum, Hatber, Tiger Enterprise),
но **49 стало хуже**: точный пул легче обнулить целиком.

**Важная поправка сессии закрытия:** это объясняет результат **заглушки**, но не
реального пула. На реальном пуле `«Цвет мела»` и `«Цвет чернил»` в обнулениях не
появляются вовсе, а «Материал» падает с 87 до 30. Механизм реального пула другой —
см. 8.5.

### 8.5. Сравнение текстового значения — главная причина обнулений на реальном пуле

Разбор: `C:\hack\diagnose_wipes_real_pool.py`, отчёт `C:\hack\build\wipes_top3.txt`.
Для каждого исключения берётся точная причина из `check_fact`, сырой фрагмент
карточки и допустимые значения позиции.

`check_fact` для `text`/`text_set` требует **точного** совпадения с допустимым
написанием. На реальном пуле (`top=3`) это даёт (числа модели A — **после** правки
§11.6, то есть класса «мусор» в них уже нет; до правки исключений было 336):

| класс исключения | модель A | харнесс |
|---|---|---|
| всего исключений в обнулённых карточках | 276 | 703 |
| значение **вкладывается** в допустимое | 85 | 121 |
| значение **составное** (`электронный+ключ`) | 21 | 15 |
| значение — уточнение в скобках (`стеллаж (комплект)`) | 0 (было 48) | 0 |
| число против текстовой характеристики | 0 (было 12) | 5 |
| имя свойства переиспользовано между позициями пула | 118 | 352 |
| значение вне словаря при уникальном имени | 52 | 209 |

До правки §11.6 **166 из 336 (49 %) исключений модели A были доказуемо не
противоречием по существу**; после неё осталось 106 из 276 (38 %) — это вложение и
составные значения, то есть уже сторона C. У харнесса таких 141 из 703 (20 %).

Примеры: `Тип патрона` «Быстрозажимной» против допустимого «Быстрозажимной патрон»;
`Тип питания` «От сети 220В» против «От сети»; сейф VALBERG, фрагмент
`Тип замка электронный+ключ` против `{Ключевой, Электронный, Кодовый механический,
Биометрический}` → ни одно не равно строке, `incompatible`, пул из 6 позиций обнулён.

Раскладка обнулённых карточек (после правки, всего 70): 31 имеет хотя бы одно
исключение-артефакт, 5 обнулены **только** артефактами, 24 — только по существу,
8 — только из-за переиспользованного имени, и **7 карточек, где исключений нет
вообще**: весь пул состоял из позиций с `resolve_blocked`, то есть пул пришёл
негодный (это к поиску, не к матчеру).

**Чья проблема.** Разделяется:
* **наша, в извлечении значений:** было 48 «мусорных» значений (45 из них — 6 карточек
  стеллажей с фрагментом `Тип стеллажа стеллаж (комплект)`, где значением стало
  уточнение в скобках) и 12 сопоставлений числа с текстовой характеристикой
  (`Высота 2000 мм` → `Регулируемые по высоте ножки/опоры`, допустимо «Да»/«Нет»).
  **Мусорные значения уже отброшены правкой §11.6**, сопоставление числа с текстом
  осталось (12 исключений у модели A, 5 у харнесса);
* **к алгоритмику, в семантику C:** 106 исключений модели A (85 вложение + 21
  составное) — вопрос, что должно означать «значение вкладывается в допустимое»;
* **к поиску:** 7 карточек с целиком `resolve_blocked` пулом.

Цена правок **на нашей стороне** измерена (`C:\hack\experiment_value_fixes.py`,
отчёт `C:\hack\build\value_fixes.txt`, `top=3`). Таблица **до** правки §11.6:

| показатель | baseline | align | garbage | both |
|---|---|---|---|---|
| дошло до кода (`resolved`) | 17 | 13 | **22** | 18 |
| пул обнулён | 76 | 72 | 70 | **66** |

* `garbage` — не выпускать факт, если значение это уточнение в скобках или огрызок
  (10 фактов): **чистый выигрыш**, +5 доведённых до кода, −6 обнулений.

  | показатель | baseline (= было `garbage`) | align | both |
  |---|---|---|---|
  | дошло до кода (`resolved`) | **22** | 18 | 18 |
  | пул обнулён | 70 | 66 | **66** |

## 10. Открытые вопросы, требующие решения

1. **`link_verified` против `type_verified`** — вопрос уточнён и частично снят.
   `can_resolve()` (`contract.py:207`) требует **все пять** условий плюс пустой

   `blocking_issues: conflicting_facts` (18 и 10). Оговорка: в моих прогонах

   мог помешать — замер говорит не «флаг не нужен», а «не он на критическом пути».

### Грабли окружения

* stdout Python здесь в **cp1251**: печать кириллицы падает с `UnicodeEncodeError`.
  Нужен `$env:PYTHONIOENCODING = "utf-8"`; отчёты писать в файл в UTF-8 и читать
  `Get-Content -Encoding UTF8`.
* `algorithms.contract.Fact` — **dataclass**, а не Pydantic: у него нет
  `model_dump()`, копия делается через `dataclasses.replace`. `model_dump()` есть у
  `app.structured.StructuredFact`, который модель A возвращает до перевода.
* `CResult.survivors` — список **строк-кодов**, не объектов позиций.
