## 1. Стадия A: текст → структура

### 1.1. `app/structured.py` — потеря смысла при переходе в контракт

| Требование ревью | Было | Стало |
|---|---|---|
| Сохранять открытость границ | `(1;2)` → `{"min":1,"max":2}`, строгость терялась | `min_inclusive`/`max_inclusive` — нотация, которую читает `AlgorithmC`; смешанные `[1;2)` / `(1;2]` поддержаны. Факт со строгой границей **жёсткий**, смысл не потерян |
| `[8;2]` не разворачивать | `min()/max()` давали `[2;8]` | границы как введены; перевёрнутый интервал контракт отвергает, поэтому факт уходит **текстом** с исходным написанием, `uncertain`, `extraction_method="reversed_interval"` |
| `(750;750)` не точка | превращалось в `number 750` | пустой интервал — тоже текст + `uncertain` + `empty_interval`, а не точка |
| «не знаю» → `uncertain` | `affirmed`, 0.86–1.0 | `uncertain`, 0.50, `unknown_value` |
| Источник не подтверждает неизвестное | `input`/`answer` давали 1.0 даже при `unknown` | сначала проверяется неизвестность, потом источник |
| «да/нет» по характеристике | тип не ставился | `boolean` только если `value_type=="boolean"` или допустимые ровно `{да,нет}`; без позиции тип определить не по чему — остаётся `text` |
| Сохранять raw/span/fact_id/единицу | `raw` не передавался | добавлено аддитивное поле `raw`; `span`, `fact_id`, `unit.text` (написание из текста) сохранены |

Независимая проверка нашла дыру, которой не было в отчёте: **«не знаю», набранное
текстом, приходит с `unknown=False`** — `app/analysis.py` ставит `unknown` только
при пустом значении. Значение-заглушка теперь распознаётся и без флага, при любом
источнике (иначе ответ «не знаю» становился жёстким фактом и исключал коды).

### 1.2. `app/extraction.py` — безопасный разбор

| Требование | Было | Стало |
|---|---|---|
| «мощностью 650 Вт» | не находилось при словаре с одним «Мощность» | имена ищутся по последовательности лемм тем же анализатором; имя приводится к написанию справочника («мощностью» → «Мощность»), исходный текст остаётся в `raw` и `span` |
| «0, 75 м» не подтверждённый ноль | факт `0` + осиротевшее «75 м» | значение «0, 75» сохраняется как в тексте, `unknown=True` → уточнение; «0,75» без пробела подтверждается как раньше |
| Множественные текстовые значения | «Цвет: красный, белый» теряло «белый» | значение сохраняется целиком; `text_set` — только если характеристика допускает несколько значений (`kind=="3"`) |
| Неподдержанные единицы | «5 футов» как обычный текст | единица сохранена как в тексте (`code=None`), факт помечен `unsupported_unit` и не подтверждён |
| Автоправка по похожести | — | «Мошность» остаётся «Мошностью»; значение не нормализуется к словарю |

Приведение имени к справочнику меняет и живой API: `fact.name` теперь
«Температура», а не «температура», как в тексте. Написание из текста не теряется
(`raw`, `span`), а сопоставление с характеристикой перестаёт зависеть от падежа.
Один существующий тест (`tests/test_pipeline.py`) фиксировал прежнее написание —
обновлён осознанно, инвариант `text[span] == raw` в нём сохранён.

Привязка `def_id` для формы «мощностью» сделана **только в мосте A→C**
(`app/structured.py`): живой путь API (`app/mapping.map_facts` → `app/checks.py`)
не тронут.

## 2. Стадия B: поиск категории

### 2.1. Порядок RRF (`app/search.py`)

Было: `sorted(ranks, key=quality)`, где `quality` — число каналов, сумма рангов и id;
сам `rank_score` в ключ не входил, поэтому кандидат с большей оценкой объединения
мог стоять ниже кандидата с меньшей. Пример ревью воспроизведён и закреплён тестом:
`score=0.038733454862487124` стоял четвёртым, а `0.038099747474747474` — первым.

Стало: первичный ключ — убывание `rank_score`; `quality` разрешает только точные
равенства (суммы RRF постоянно совпадают: у одиночного лидера канала 1/61). Та же
формула есть в коммите команды; здесь она вынесена в `_rank_order`, чтобы дефект
проверялся напрямую. Инвариант проверен на полном индексе: **46 запросов, нарушений
порядка — 0**.

### 2.2. Маленькие каталоги (`CharNgramIndex`)

`min_df=2` удалял все n-граммы названия, не похожего на остальные: документ
становился невидимым и получал нули даже на точном совпадении (в ревью — все четыре
названия мини-каталога). Команда исправила это значением `min_df=1`; правка
оставлена как есть.

Замер обеих схем (`C:\hack\build\min_df_choice.txt`): на независимом наборе
результат **одинаков** (те же 4 промаха из 46, те же цифры по группам), но `min_df=1`
даёт 8163 постинга против 6295 — лишние 1868 грамм встречаются в одном документе.
Оставлен вариант команды: он проще и даёт редкой грамме максимальный idf, то есть
работает как точное совпадение подстроки. Мой эквивалентный механизм «возврата
грамм невидимому документу» удалён, чтобы не было мёртвого кода.

### 2.3. Перефразировки (`app/synonyms.py`, `app/category_map.py`)

Причина промахов не в объединении рангов: в поисковой записи семьи нет слов о
назначении товара. Добавлен слой назначений — онтология по **классам** товаров и
шаблоны формулировок; кодов КТРУ и конкретных семейств в нём нет. Якорные шаблоны
подобраны по каталогу: слой задевает **7 семейств** из 14 550 (2 дрели, шуруповёрт,
2 шкафа для документов, офисное кресло, туристический рюкзак) и **не задевает**
кресла-коляски (33 семьи), медицинские перфораторы и хирургические дрели — это
проверено тестом.

### 2.4. Неверная раскладка и смешение алфавитов (`query_variants`)

Добавлены безопасные поисковые варианты: ЙЦУКЕН↔QWERTY для текста без кириллицы и
замена латинских двойников внутри токенов, где кириллица уже есть. Исходный запрос
всегда первый, варианты объединяются по максимуму на документ и не могут ухудшить
его оценку. Токены с цифрами и разделителями (коды, ГОСТ, артикулы) не
переписываются; латинские названия целиком не трогаются. Пользовательские
характеристики и факты не меняются — это только поисковый запрос.

## 4. Проверка раннером ревью

`python tests/run_independent_review.py <отчёт>` (раннер команды, повторяет
приложения ревью) на текущем дереве:

| Группа | Было (отчёт команды) | Стало |
|---|---|---|
| A-contract | 4/6 | 4/6 |
| A-extraction | 7/12 | **10/12** |
| B-char | 4/4 | 4/4 |
| B-fusion | 1/1 | 1/1 |

Оставшиеся «провалы» — осознанные расхождения теста ревью с его же прозой и с
поставленной задачей:

1. `boolean_да` / `boolean_нет` — скрипт ревью вызывает `structure()` **без
   позиции**, а характеристика неизвестна. Определять «да/нет» как `boolean` без
   неё — это и есть универсальная типизация, которую запрещено делать. С булевой
   характеристикой A выдаёт `kind="boolean"`, `value=True/False` (покрыто тестом).
2. `typo_property` («Мошность» → «Мощность») — автоправка запрещена; команда уже
   реализовала поток подтверждения (`app/correction_flow.py`), и A намеренно
   сохраняет написание.
3. `space_comma` («0, 75» → «0,75») — это тоже автопереписывание пользовательского
   значения. Требование «не должно становиться подтверждённым нулём» выполнено
   иначе: значение сохраняется как в тексте и уходит на уточнение.

## 8. Согласование контракта с владельцами C/D

1. **Строгие границы — согласовано.** Нотация `min_inclusive`/`max_inclusive`
   принята обеими сторонами: `AlgorithmC.check_fact` читает эти ключи, A их
   отправляет, факт со строгой границей остаётся жёстким. Ключи
   `min_notation`/`max_notation` остаются только во внутреннем представлении
   индекса КТРУ и в фактах A не используются.
2. **Поле `raw`.** Аддитивное поле с исходным фрагментом; `Fact.from_dict` лишние
   ключи игнорирует, round-trip проверен тестом. Если C захочет видеть
   происхождение факта, поле готово.
3. **`text_set` для нескольких значений** — только там, где характеристика
   допускает несколько значений (`Property.kind == "3"`). Более широкое правило
   («слово + число + единица» как разделитель фактов) требует решения владельца
   контракта.
4. **Признак `unknown` при неподдержанной единице**: A помечает факт
   неопределённым на своей стороне, но не ставит `Fact.unknown` в схеме API (иначе
   меняется код причины в HTTP с `unit_unknown` на `unknown_fact`).
5. **Имя факта из справочника.** A приводит имя к написанию характеристики, когда
   форма слова подтверждена леммами. Если C ожидает строго текст пользователя —
   это одна строка в `app/extraction.py:canonical_name`.
