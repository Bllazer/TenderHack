## Требует решения backend — по приоритету

### 1. `OKEI_SUPPORTED`: три кода. Блокирует финальную поставку

| Код | Сейчас | Должно быть |
|---|---|---|
| `050` | `см²` | **Квадратный миллиметр** (см² — это `051`) |
| `271` | `Ом` | **не Ом** (Ом — это `274`) |
| `274` | нет | **Ом** |

Почему срочно: отсутствующий код даёт честный `unsupported` и блокирует позицию —
это безопасно. А **неверный код проходит как проверенный**. `050` проставлен
1 097 раз, `271` — 94. Итог: **112 конечных позиций принимают неправильную единицу
как проверенную** и могут дойти до `resolved` с неверным сравнением величин.
Ошибка молчаливая, текущими проверками не ловится.

После правки шаги 2–3 из `ML_DELIVERY.md §8` повторить. Порядок и связи не
изменятся, SHA — изменятся.

### 2. Порог значимости в `Search.find` — или решение оставить как есть

`find` **всегда возвращает 5 кандидатов**. Когда совпадений нет, каждый кандидат
получает 1/61 (первое место в одном канале) и выдаётся пользователю как обычный
результат.

Проверено фактами: «Грабли» и «Панама» **отсутствуют в каталоге** (0 позиций,
каталог содержит только действующие — 60 087 из 181 492). На запрос «панамка»
пользователь видит «Нож для тимпанотомии».

Предложение: если ни один токен запроса не встречается в индексе (df = 0 для всех
токенов) — возвращать пустой список. Это **меняет контракт `find`** и влияет на
поток подтверждения категории, поэтому сам не трогал. Сейчас предупреждение есть
только в моём CLI.

### 5. Семантика `link_verified`

В `analysis.py` флаг читается как `type_verified`. Мы ставим `True` для семей,
проверенных **структурно** (связи `parentPositionInfo`, отсутствие циклов, полнота
перечисления — все 54 190 конечных позиций), и это записано в `evidence`.

Вопрос: структурной проверки достаточно для `type_verified`, или под флагом
понимается содержательная предметная проверка типа? Второе автоматически не
делается, ручная проверка 14 550 семей нереальна.

### 6. Формат ссылки при сжатии `raw_json`

`Property.raw_json` дублирует объект характеристики, уже лежащий в
`Position.raw_json`, и **нигде не читается в runtime**. Предлагаю заменить на
`{"ref":"<код позиции>#<код характеристики>","origin":"position.raw_json"}`.

Замеры в отдельных процессах: файл 812 → 706 МБ (−13 %), RAM 2.39 → 2.18 ГБ,
пик 6.26 → 5.64 ГБ. Включается флагом `--compact-raw`, по умолчанию выключено —
нужно согласование формата.

## Мелочи, но стоит знать

- **API не проверяет кодировку тела.** При cp1251 вместо UTF-8 сервис не вернёт
  ошибку, а уверенно выдаст мусорные категории. Воспроизвёл случайно.
- **`clean_supply_dir`** по умолчанию `../ktru_clean`, Compose монтирует
  `./ktru_clean` — в репозитории такой папки нет. Локально нужен явный
  `CLEAN_SUPPLY_DIR`.
- **Старт сервиса ~17 с**: 10 с каталог + 6 с модель. Ждать `/api/health/ready`,
  а не сразу дёргать запросы.
- **Мёртвые кандидаты:** позиции с 0 характеристик (`no_characteristics`)
  всплывают первыми в выдаче, но до `resolved` дойти по ним нельзя.
