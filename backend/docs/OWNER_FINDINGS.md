каталоге `catalog_version=clean5-578e29f99d1a803c` (14 550 семейств).

Прогоны после правок: `pytest -q` — **575 passed, 49 skipped**; с `RUN_E5_TESTS=1` и

(было 10), exact top-5 **16 из 16**; контрольные запросы поставки — 7 из 8 (без изменений,
известный промах-перефразировка).

## 1. Одна конечная позиция — сразу результат

**Как сейчас.** Если в пуле осталась одна позиция, система всё равно спрашивает
обязательные поля («Укажите: Минимальный диаметр зажима патрона», «Нужно для проверки
обязательного поля»), хотя выбор уже однозначен. Воспроизведение: заключение
`28.24.11.000-00000002` — «Конечные позиции: 1» и вопрос о характеристике.

**Почему так.** Контракт требует доказанного значения для вопроса о коде
(`ready = unique and value_verified and fields_complete and scope_complete`): пока
обязательное поле не заполнено, вопрос о коде не задаётся, и вместо результата
показываются вопросы о полях.

**Что делать.**
* **Фронтенд:** при `candidate_count == 1` открывать шаг «3. Результат» (пул уже
  однозначен; незаполненные поля показывать в блоке «Проверка не завершена · Требуется: …»,
  он уже есть на скриншоте). Это правка навигации, данные для неё в ответе есть.
* **Бекенд (опционально):** при `unique` предпочитать вопрос о коде вопросам об
  обязательных полях, оставив незаполненные поля замечаниями (`verification_incomplete`).
  Решение продуктовое: код подтверждает пользователь, поэтому «resolved» по-прежнему
  требует полей — иначе пропадёт доказательность.

## 2. «Панамка»: нет товара — нет подсказок

**Как было.** Поиск всегда возвращал пять категорий: «Нож для тимпанотомии» (0.0258),
«Креативная панель» (0.0196) и т. д. — на товар, которого в КТРУ нет.

**Как стало.** Оценки объединения (RRF) откалиброваны на реальном каталоге: у запросов,
для которых семейство существует, минимум **0.0492** (медиана 0.0651); у несуществующих
товаров максимум **0.0328** («панамка» 0.0258, «кофеварка» 0.0328, «drel» 0.0164).
Появился порог `SIGNIFICANCE = 0.040` (`app/search.py`) и словесный фильтр: пустой ответ
только когда и лучший кандидат слабее порога, и ни в одном названии нет слова запроса
(точного, по лемме, по началу слова или почти написанного).

```
«панамка» → поиск: пусто; API: candidate_count=0, issues=['no_similar_products'],
            next_question=null, next_steps=['Ничего похожего не найдено — уточните описание товара']
```

**Что нужно от фронтенда:** показать формулировку при пустом списке категорий
(сейчас, вероятно, отрисуется пустой блок). Код проблемы в API: `no_similar_products`.
Порог — свойство каталога (`Search(..., significance=…)`), для тестового стенда он
отключён: там оценки структурно ниже.

## 3. «Шпа»: шпажки, а не шпагат

**Причина.** «шпа» — не слово каталога: BM25 молчит, а char/e5 выше ставили
«Канаты, веревки, **шпагат** и сети…» (совпадение внутри длинного названия).

**Что сделано.** Четвёртый канал `PREFIX`: слово запроса в начале слова названия,
совпадение первого слова весит вдвое больше, длинное совпадение — больше короткого.
Плюс ярус: для коротких запросов (одно слово до пяти букв) кандидаты с совпадением
первого слова идут выше. Результат:

```
«шпа»     → Шпатель | Шпала деревянная | Шпатель лабораторный | Шпатель стоматологический |
            Шпалы железобетонные | Шпажки для канапе | Шпатель мозговой      (шпагата нет)
«шпажки»  → Шпажки для шашлыка | Шпажки для канапе        (ровно две, без добивки)
```

## 4. Дубли категорий

**Измерено.** 893 имени имеют дубли; у 135 из них характеристики **различаются**:
«Протез пениса жесткий» — 16 семейств с 16 разными наборами характеристик,
«Канаты, веревки, шпагат…» — 4 семейства с одинаковыми.

**Что сделано (показ).** В выдаче одноимённые семейства больше не повторяются: остаётся
лучше ранжированное. «пенис» теперь показывает 7 разных типов (Протез жёсткий, Зажим,
Шина, Протез надувной, Мочеприемник, Уропрезерватив×2), а не 4× одно и то же.

**Что нужно от бекенда (полное решение).** Сливать одноимённые семейства в **один пул**:
при сборке снимка объединять корневые семейства с совпадающим `canon(name)`, складывая
`position_codes`, а `link_verified`/`coverage_verified` объединять по «И» с сохранением
исходных id в `evidence`. Сейчас выбор показанного семейства даёт пул только его
позиций: у «Протеза пениса жёсткого» пользователь увидит позиции одного из 16 вариантов.
Показ я сократил, пул — нет, потому что это семантика каталога, а не поиска.

## 5. «Дерл»: нужна «дрель ручная электрическая»

**Причина.** Слово короче пяти букв не исправлялось, а `difflib` не считает перестановку
одной правкой: у «дерл» похожесть к «дрель» 0.667, а к «дел» — 0.857, то есть выбиралось
неверное слово.

**Что сделано.**
* Расстояние Дамерау-Левенштейна: перестановка соседних букв — одна правка.
* Исправление ищет слово **не короче** написанного (пользователь не дописал или перепутал
  буквы, а не выбросил корень): «дерл» → «дрель», а не «дел».
* Минимальная длина исправляемого слова — 4 буквы.

```
«дерл» → Дрель ручная механическая | Дрель хирургическая ручная | Дрель ручная электрическая | …
```

## 6. Транслит и раскладка

«drel» больше не показывает мусор: пустой ответ и `no_similar_products` — порог
значимости отсекает и латинский ввод, и его раскладку («вкуд»). Раскладку (QWERTY→ЙЦУКЕН)
я **оставил** намеренно: это частая ошибка русского ввода («lhtkm» → «дрель» — рабочий
случай, проверен тестом). Если нужно убрать и её — скажи, это одна строка в `query_variants`.

## 7. «Пальто муж 48»: сокращённый пол

**Что сделано.** Ступень сокращений значений перечислений (`abbreviated_enum_values`):
«муж» → «Мужское», «жен» → «Женское», «аккум» → «От аккумулятора», «от сет» → «От сети».
Правила: слово не короче трёх букв, не служебное, это **строгое** начало слова значения,
и подходит ровно одному значению ровно одного свойства. Первое слово многословного
значения не годится: «искусственный» не становится «Искусственный утеплитель» — для
такого значения нужен весь оборот (это требование набора проверок перечислений).

```
ввод: «пальто муж 48», категория подтверждена
факты: Российский размер = 48; Половой признак = Мужское
следующий вопрос: «Укажите: Натуральная кожа» (пол больше не спрашивается)
```

Заодно поправлено сопоставление по `enum_targets` для явных пар («пол: муж»).
