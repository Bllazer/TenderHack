# Правила моделей A и B: свод и проверка по факту

Документ отвечает на две вещи: (1) что из списка владельца уже работает и чем это
подтверждено, (2) какие правила действуют в коде дополнительно, хотя в списке их не было.

Все примеры ниже — вывод прогонов, а не описание замысла. Артефакты: настоящий каталог
`resources/catalog-build` (14 550 категорий, позиция `28.24.11.000-00000003`
«Дрель ручная электрическая»), модель `intfloat/multilingual-e5-small` ревизия
`614241f622f5…`, фикстура `tests/fixtures/verified.json` для HTTP-примеров.

## Часть 1. Шесть правил владельца

| № | Правило | Статус | Как сделано | Чем подтверждено |
|---|---|---|---|---|
| 1 | Выявлять категорию товара и его характеристики | ✅ | Поиск (модель B) предлагает категории, пользователь подтверждает; характеристики берутся **только** из подтверждённой области | HTTP: «Дрель электрическая; питание: от сети» → вопрос `kind=category`, варианты «Дрели электрические / Столы / Рабочие куртки»; после подтверждения — факты по свойствам области |
| 2 | «650вт», «200см»: если характеристика однозначно определяется единицей — расписать | ✅ реализовано | `app/extraction.py::bind_bare_measurements` и `app/model_a.py::bind_measurements`: размерность единицы называет характеристику, если она в области **одна** | «дрель 650 вт» → `Мощность = 650 вт` (def_id `d4`, ОКЕИ 212, 0.95); «стол 200 см» → `Высота = 200 см`; «дрель 650 вт 220 в» → `Мощность` + `Напряжение аккумулятора` |
| 3 | Если однозначно определить нельзя — уточнить у пользователя | ✅ реализовано | Вопрос `kind=correction`: «Что означает «5 мм»?» с вариантами-характеристиками и «Это дополнительные сведения»; ответ становится явной правкой, значение берётся из текста | «…5 мм» при двух свойствах в мм → вопрос с «Минимальный диаметр…» / «Максимальный диаметр…» / «дополнительные сведения»; `accept` → факт `5 мм` и `resolved`; `reject` → факта нет, подбор не блокируется; ответ вне диапазона → отказ `incompatible_ktru_code` |
| 4 | Опечатка, и слово известно — заменить самому | ✅ | Автозамена при похожести ≥ 0.85 (та же первая буква, ≥ 5 букв, ровно один кандидат) + провенанс `Correction(confirmation_required=false)`, исходный текст остаётся в `raw` | «Мошность 650 Вт» → факт `Мощность`, `raw` = «Мошность 650 Вт», вопроса нет |
| 5 | Не знаю / не уверена — попросить уточнить | ✅ | Похожесть 0.72…0.85 → вопрос «Возможно, вы имели в виду «Высота»?» с вариантами «Это «Высота»» / «Это дополнительные сведения»; до ответа факт мягкий (0.58) | «Высата 750 мм» → факт с написанием пользователя + вопрос; после `accept:Высота` — факт `Высота = 750 мм` |
| 6 | Как только запрос обработан — отправить в модель B | 🔶 порядок другой | Фактически: **B** предлагает категорию → пользователь подтверждает → **A** извлекает факты в этой области → **C** проверяет пул позиций из B → **D** подтверждает код. B участвует дважды (категория и пул), A — после подтверждения области | См. `docs/ML_STATE.md` §10.1; порядок виден в `app/analysis.py` |

**Что было не так с правилом 3 и что исправлено.** До этой правки неоднозначное
измерение оставляло анализ в `needs_input` **без единого вопроса** — с одной лишь
записью «В исходном тексте осталось измерение без установленного свойства». Пользователь
не мог ничего ответить: тупик. Теперь по такому измерению задаётся вопрос с конкретными
вариантами (или хотя бы «это дополнительные сведения», если подходящих характеристик нет
вовсе).

## Часть 2. Правила, которые действуют в коде, но в списке их не было

1. **Уверенность решает, можно ли исключать код.** `≥ 0.6` — факт жёсткий: C исключает
   по нему коды. `< 0.6` — мягкий: C проверяет, но **никогда** не исключает. Ступени:
   exact 0.95, lemma 0.90, typo(автозамена) 0.90, alias_lemma 0.75, fuzzy 0.58,
   partial 0.55, unmatched 0.0.
2. **Имена характеристик берутся только из подтверждённой области.** Предложения по
   всему каталогу (15 000+ имён) не делаются: без `confirmed_category_id` извлечение
   работает по общему словарю имён, но факты не сопоставляются с конкретной позицией.
3. **Значения не проверяют ни A, ни B.** Совместимость решает C: диапазоны, перечисления,
   строгие границы, размерности, OR-альтернативы. A отвечает за «что написано», B — за
   «что это за товар».
4. **Единица сохраняется как написана**, перевод в единицу характеристики делает C
   перед сравнением: «0,65 кВт» → сравнение с диапазоном 500…800 **Вт**.
5. **Не выдумывать текстовое значение при неподтверждённом имени.** «Высата Полиэстер»
   факта не даёт: имя в уровне подсказки, значение не измерение.
6. **Пустое значение не выпускается фактом.** Факт без утверждения исключал бы позиции,
   ничего не сообщая.
7. **Отрицание распознаётся** («без реверса») и не превращается в значение.
8. **Числа не участвуют в поиске типа товара.** Единственное исключение — вариант запроса
   без измерений, и он берётся только если после удаления остаётся ≥ 2 слов и единица
   стоит после числа. Иначе «дрель 650 Вт» превращалось бы в «дрель» и уезжало в
   «Дрель ручную механическую».
9. **Варианты запроса только добавляются** (раскладка, гомоглифы, опечатки, измерения):
   исходный запрос никогда не подменяется, каналы берут максимум по вариантам.
10. **Пул — до 5 кандидатов без порога значимости**; шаблон/семейство не может быть
    итоговым кодом; если подтверждён несовместимый код — отказ `incompatible_ktru_code`.
11. **Итоговый код подтверждает пользователь** (D). Модель никогда не выбирает код сама.
12. **Незакрытый вопрос блокирует выбор кода**: пока есть `pending` (коррекция имени,
    измерение, свойство), `value_verified` ложно.
13. **Полнота области проверяется**: если связи и конечные позиции области не
    подтверждены, добавляется `insufficient_catalog_coverage`.
14. **Если совместимых позиций нет — говорят причину**, а не показывают ближайший код:
    `out_of_range`, `no_compatible_candidate` и т. п.
15. **Порядок слов не важен**: «650 Вт мощность» и «Мощность 650 Вт» дают один факт;
    «20 см молоток» и «молоток 20 см» — один и тот же top-1 с тем же score.
16. **Критерий автозамены опечаток замерен**: на 774 однобуквенных опечатках похожесть на
    истинное имя имеет медиану 0.900; выше 0.85 попадает 80 % опечаток и **ни одной**
    спорной (чужое имя тоже ≥ порога), максимальная похожесть на чужое имя — 0.833.
    Порог автозамены 0.85, порог подсказки 0.72. Окна с цифрами не рассматриваются
    («Мощность 0» в «Мощность 0,65 кВт» давало ложное совпадение).
17. **Привязка по единице требует двух условий**: подтверждённая область и ровно одна
    числовая характеристика этой размерности. Иначе — вопрос (правило 3).
18. **Неполное имя характеристики привязывается, если оно однозначно.** «минимальный
    диаметр» — строгое подмножество лемм ровно одного имени («Минимальный диаметр зажима
    патрона») → факт создаётся с написанием пользователя, характеристика ставится
    (`def_id`), но факт **мягкий**: `extraction_method = partial_name`, уверенность 0.55
    (ниже порога 0.6). Если подмножество подходит двум именам («диаметр» — и минимуму, и
    максимуму), привязки нет: значение уходит вопросом (правило 3). Модель A ведёт себя
    так же (ступень `partial`, 0.55); до этой правки она выбирала первый по порядку
    кандидат — исправлено на единственность.

## Часть 3. Что осталось и что предлагается

1. **Порядок «A, потом B»** (правило 6 в буквальном чтении) — это смена оркестрации:
   сейчас B нужен раньше, потому что он предлагает категорию, без которой A не знает
   область. Если хотите строго «A → B», нужно решить, откуда берётся категория.
2. **Число как признак типа товара.** Сейчас «650 вт» не влияет на выбор семейства
   (только на проверку значения). Если нужно, чтобы мощность различала «от сети» и
   «аккумуляторную», это отдельное правило с отдельными замерами. По решению владельца
   **не делаем**.
3. **Опечатки ниже 0.72 не предлагаются** («толщена» 0.714): понижение порога добавит
   вопросы на законные слова — цена измерена в `QUERY_VARIANTS_REPORT.md` §6.2.

## Часть 4. Как это воспроизвести

```powershell
$py = "C:\Users\geome\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"
Set-Location C:\hack\TenderHack\backend
$env:PYTHONIOENCODING = "utf-8"; $env:PYTHONUTF8 = "1"
$env:HF_HUB_OFFLINE = "1"; $env:TRANSFORMERS_OFFLINE = "1"

# правила 2–3: привязка по единице и вопрос про неоднозначное измерение
& $py -m pytest -q tests/test_stage_a.py tests/test_pipeline.py
& $py C:\hack\probe_rule3_answers.py        # вопрос, accept, reject, отказ

# правила 4–5: два уровня опечаток
& $py -m pytest -q tests/test_correction_http.py tests/test_stage_a.py

# правила 1 и 6: порядок оркестрации и пул
& $py -m pytest -q tests/test_pipeline.py tests/test_correction_http.py

# всё вместе
& $py -m pytest -q
```

Проверки на момент документа: `pytest -q` — **493 passed, 37 skipped**; с `RUN_E5_TESTS=1`
и полной поставкой — **530 passed**; аудит независимого ревью — A-extraction 11/12,
C 23/24, границы 28/28, единицы 9/9, B-fusion 1/1, API 24/24, сетка 90/90, штатные C/D 28 OK.

Новые проверки этой правки: `tests/test_stage_a.py` (неполное имя привязано и мягкое,
двусмысленное не привязано, одно слово привязано мягко, полное имя не понижается),
`tests/test_pipeline.py` (вопроса про измерение нет, значение вне диапазона позицию не
исключает), `tests/test_model_a.py` (неполное имя не подменяет написание).
