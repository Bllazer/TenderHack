# Исследование кейса и схема данных — 9 октября 2026

Историческая записка: описанная ниже схема БД больше не относится к рабочему приложению. Текущая архитектура stateless, без БД; действующие контракты — [API.md](API.md), [CATALOG.md](CATALOG.md) и [README](../README.md).

## Что требуется

Официальная страница [Tender Hack Казань](https://tenderhack.ru/kazan) ставит задачу автозаполнения ключевых характеристик СТЕ для [Портала поставщиков Москвы](https://zakupki.mos.ru/). Ожидаются подбор унифицированных характеристик из предоставленного датасета и КТРУ, сопоставление значений и единиц, поэтапное сужение кода, запрос уточнений при неоднозначности, выявление и объяснение ошибок, веб-интерфейс, тесты на неполных данных и BPMN для презентации. Задачи на странице обозначены как опциональные, поэтому объём MVP нужно согласовать с командой и организаторами.

СТЕ — карточка позиции Портала поставщиков с наименованием, изображением и характеристиками: [справка портала](https://zakupki.mos.ru/knowledgebase/article/details/ais/214180). [Инструкция по созданию СТЕ и оферты (2026)](https://zakupki.mos.ru/cms/Media/docs/%D0%98%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%86%D0%B8%D1%8F%20%D0%BF%D0%BE%20%D1%81%D0%BE%D0%B7%D0%B4%D0%B0%D0%BD%D0%B8%D1%8E%20%D0%BE%D1%84%D0%B5%D1%80%D1%82%D1%8B%20%D0%B8%20%D0%A1%D0%A2%D0%95.pdf) различает основную информацию, категорию и характеристики, происхождение и цены. Страница [каталога КТРУ ЕИС](https://zakupki.gov.ru/epz/ktru/start/startPage.html) и [пример описания позиции](https://zakupki.gov.ru/epz/ktru/ktruCard/ktru-description.html?itemId=58.29.11.000-00000003) помогают проверить структуру кода и признака обязательности характеристики. ЕИС `zakupki.gov.ru` — источник КТРУ, а целевой процесс СТЕ находится в `zakupki.mos.ru`; не смешивать идентификаторы карточек и КТРУ.

Доступность прямой программной выгрузки КТРУ/СТЕ, лицензия и точный формат организаторского набора на момент создания проекта не подтверждены. Нет оснований обещать работающий FTP либо неофициальный endpoint ЕИС. При поступлении набора нужен один преобразователь `исходный файл -> нормализованный JSON -> app.import_catalog` с версией источника, проверкой типов и идемпотентной загрузкой. Демонстрационный набор в проекте полностью синтетический и использует коды `DEMO-*`.

## Минимальная модель

| Таблица | Зачем | Ключи |
| --- | --- | --- |
| `categories` | Иерархия/листовые позиции КТРУ | `ktru_code` уникален, `parent_id`, `source_version` |
| `attributes` | Словарь признаков, типы, единицы и синонимы | `name` уникален |
| `category_attributes` | Какие признаки применимы к коду, обязательность и допустимые значения | уникальная пара `(category_id, attribute_id)` |
| `ste` | Исходная карточка Портала/организаторов | уникальная пара `(source, external_id)`, `raw_payload` |
| `analyses` | Вход, версия алгоритма и объяснимый снимок результата | `ste_id` опционален |
| `feedback` | Принятие, отказ и поправки для будущей оценки качества | `analysis_id` |

Текущая схема принимает строковые значения единиц и допустимых вариантов, не угадывает физические преобразования. После реального набора оценить отдельные таблицы единиц, идентификаторы характеристик источника, значения диапазонов/условные операторы и связанные с версией источника правила. Сравнивать КТРУ на уровне конечной позиции; не объявлять промежуточный узел окончательным кодом.

## Где взята архитектура

- [Официальный Full Stack FastAPI Template](https://github.com/fastapi/full-stack-fastapi-template): разделение backend, Postgres, Docker Compose, Pydantic, тесты и клиент по OpenAPI. Здесь взята компактная часть стека без чужого React, auth и прокси.
- [Документация FastAPI по SQL БД](https://fastapi.tiangolo.com/tutorial/sql-databases/) и [SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html): сеанс на запрос, короткая транзакция, отдельные входные/выходные схемы.
- [Alembic migrations](https://alembic.sqlalchemy.org/en/latest/autogenerate.html): версионирование структуры БД; первая миграция написана явно.
- [Решение TenderHack 2025 one-zero-eight](https://github.com/one-zero-eight/hackathon-tenderhack): референс именно для разделения frontend/backend/ML и Docker, но его задача группировки СТЕ отличается от задачи Казани 2026. Не копировать его модель данных вслепую.

## Вопросы при получении данных

1. Каковы точные идентификаторы КТРУ/категорий/характеристик и можно ли связывать СТЕ с КТРУ один к одному?
2. Какие значения категориальные, числовые, интервальные; какие единицы и конвертации действительно разрешены?
3. Есть ли эталонные пары `описание -> характеристики -> КТРУ`, отдельная тестовая часть и критерий оценки?
4. Что делать с несуществующим кодом, несколькими равноправными кодами, товаром без перечисленных характеристик?
5. Разрешено ли использовать данные вне предоставленного набора; нужен ли offline режим на защите?

## Ближайшая интеграция моделей

Стабильная граница: `app.analysis.analyze(session, attributes)` возвращает `(status, AnalysisResult)`. Первым делом добавить текстовый extractor и нормализатор как отдельные функции, передавать `title/description`, сохранять происхождение каждого значения (`input`/`description`) и обоснование. Затем ранжировать кандидатов, но `resolved` разрешать только при калиброванной уверенности и подтверждённых правилах. Измерять top-k recall кода, F1 по извлечённым атрибутам, точность единиц, долю честных уточнений и latency на отложенном наборе.
