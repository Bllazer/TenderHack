# Этап 1: достоверное исключение не отменяется неизвестным ограничением

База: main `e7a1f6d`. Перед началом status содержал только пользовательский
untracked ktru_clean/, fetch origin main подтвердил отсутствие новых коммитов
после e7a1f6d и расхождения 0/0. Исходники алгоритмов, адаптер поставки, каталог,
индекс и модель не менялись. Следующий этап не выполнялся.

## Изменения и основание

В app/analysis.py необусловленный unknown заменён понижением только совместимой
или ещё не проверенной позиции. В app/checks.py тот же приоритет сохранён при
source_issues/resolve_blocked; правило с unsupported_reasons не доказывает
исключение, даже если verified ошибочно осталось true.
Изучены catalog_diagnostics.py, algorithm_adapter.py и AlgorithmC:
адаптер уже сохраняет incompatible строгой проверки; C при наличии exclusions
ставит incompatible прежде неизвестности, но не проверяет resolve_blocked-позиции.
Это не отменяет доказанное проверенным backend-правилом противоречие.
Неподдержанные/неподтверждённые поля по-прежнему не доказывают совместимость.

Candidate.exclusion_reasons сохраняет объяснение, fact_id/property_id и
rule_source противоречия. Checks и blocking_reasons остаются в excluded.
Ошибки исключённой позиции не становятся блокировками оставшегося пула.
API.md, Pydantic/OpenAPI и frontend/src/api.ts согласованы; UI не изменён.

Основание ожидаемого сужения — допустимые значения исходных характеристик
реальной поставки, сверенные с raw_json карточек. Отчёты команды не использованы
как oracle. Оригинальные XML/XLSX в этих проверках не читались: подтверждена
согласованность действующей clean (5) поставки и адаптированного snapshot,
а не повторная независимая валидация XML-конвертера.

## Реальные запросы и результат до/после

Полные HTTP-запросы/ответы (включая GET карточек, manual confirmation и версии)
сохранены в [before.json](before.json) и [after.json](after.json).
after.json включает фактический OpenAPI и независимо выведенные source_proofs.
Каждый POST передаёт description, confirmed_category_id и candidate_limit=100.
Скрипт находит ID семейства по исходной записи шаблона, не по списку ожидаемых кодов.
В API работают настоящие модель, индекс и поиск; подмены ресурсов нет.

Коды таблицы — наблюдаемый результат, не oracle теста. Ожидаемые исключения
вычисляются из исходных values выбранных реальных позиций и текущих фактов,
при подтверждённых применимости/происхождении и поддержке правила.
После исправления ни один incompatible-check не находится в candidates.
Manual confirmation исходно противоречащей позиции: до — 200 needs_data,
после — 422 incompatible_ktru_code во всех пяти сценариях.

Все пять итогов остаются needs_data, selected_ktru_code=null:
kind=3 и прочие blockers оставшихся позиций сохранены. Лопата:
«Конструктивные особенности»; молоток: «Форма бойка»;
пальто: «Тип утеплителя». Полный точный список см. blocking_reasons в after.json.
Карточка фактов сохранена даже при невозможности завершения: мужское пальто
48 размера содержит «Половой признак: мужское» span=[7,14] и
«Российский размер: 48» span=[15,17], с исходными raw и происхождением.
